# P2 实施计划评审意见

评审时间：2026-09-18 10:47 (+08:00)
结论：**批准执行**，附 4 个必须项（M1–M4）与 3 个建议（S1–S3）。

## 必须项

### M1 `/api/config/active` 热更端点存在能力虚构风险（同 Q6 教训）
open-llm-vtuber 的 ASR/TTS 引擎在 ServiceContext 初始化时装载进内存，"新增路由动态热更端点"不是写路由就能生效的——LLM 端点（URL/key）热更相对容易，但 ASR/TTS 本地↔云端切换涉及引擎实例重建。计划对此零描述。
**要求**：二选一——① 复用现有 `handle_config_switch` 机制（预置多个 conf alt yaml，整配置切换，已被验收）；② 明确写出引擎重建策略与降级路径。不允许出现"路由返回 200 但引擎没换"的假热更。验收时须实测：切换 ASR 端点后发一句话，证据里能看到走的是新端点。

### M2 设置窗口生命周期未定义——又一个内存炸弹
settings.html 是第二个 WebView2 实例（+100~200MB 树）。若常驻，休眠态 ≤45MB 目标直接破产。
**要求**：设置窗口"用后即毁"——关闭即 destroy，不留存；验收的休眠态测量必须覆盖"开过设置再关闭"的场景。

### M3 模型热切换的在飞 turn 与持久化
- llama-server 被杀重启的 2.58s 内，在飞对话会失败：需明确切换期间 UI 置"切换中"并阻断新提问（配合 turn_id 防线，旧 turn 被 suppress 可接受，但要写清）；
- `switch_model` 后必须回写 services.json 的模型路径，否则下次冷启静默回到旧模型（状态漂移）。

### M4 重建耗时口径分层
≤800ms 若含 WebView2 进程拉起+页面加载+WS 重连+Live2D 装载，偏紧（Chromium 冷起常 1-2s）。
**要求**：拆两个数字——"窗口可见"与"可对话（WS ready）"分别测量分别达标，禁止合并成一个看似达标的均值。

## 建议项

- **S1 DPAPI 威胁模型写准确**：CryptProtectData 默认当前用户 scope，防的是"文件被拷走到他机/他人"，**同机同用户的其他进程可解密**——不是计划里写的"硬件级"。建议加 entropy 参数提高一阶，文档措辞改为"用户级凭据加密"。
- **S2 W:\model 递归扫描限深**（建议 ≤3 层），避免大目录首扫卡顿；扫描放后台线程，结果缓存。
- **S3 上轮遗留趁此闭环**：frontend/index.html 的 pet-mode 定制至今不在任何 git 仓库（submodule 无 .git）。P2 又要改 ui/settings.html，建议把前端定制纳入版本控制（fork 仓、patch 文件或 acceptance 哈希清单任选其一），否则桌面壳的前端资产始终处于无版本状态。

## 验收追加一条
设置热更（LLM 模型/ASR/TTS 端点/角色）完成后，复跑 live acceptance Test A–E，证明配置切换后链路行为仍正确——配置热更的正确性不能只看路由返回。
