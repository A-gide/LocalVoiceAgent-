### 但我发现一个**新的行为特征**（须报告，不是缺陷判定）

```ini
round 1: imported=1 watermark=0 stored=1     # 坏记录 + 1 条有效
round 2: imported=0 watermark=0 stored=1
round 3: imported=0 watermark=0 stored=1

再追加 5 条有效记录后：imported=5 watermark=0 stored=6
-> BEHAVIOUR: the checkpoint is blocked while the bad record is unimportable
```

**性质**：坏记录**永不修正**时，水位**永久阻塞**。有效记录仍会入库（靠唯一约束去重），

**这是设计权衡，不是缺陷**——「不推进水位」正是保证可补入的代价。但它带来两个后果需要 T01 明确：

1. **范围永不闭合**意味着每次导入都会重扫自起点以来的全部记录（去重后无副作用，但**吞吐随历史增长而下降**）；
2. 需要一个**运维出口**：坏记录处理策略（人工修正 / 显式放弃 / 隔离后推进水位）目前未定义。

**建议并入 T01 验收**：明确「坏记录长期存在时的预期行为」并给出可操作的处理路径，否则 T08 的性能测量会把这一项混入「吞吐」而看不出原因。

## 8. 更正（同日二次复现，覆盖 §3 的「已修复」结论）

§3 的探针把坏记录与有效记录**放在同一页**，于是看到「坏记录在场 → 水位不动」，据此判为已修复。**那个前提是错的。**

真正的缺口要求水位**先**推进、坏记录**后**出现：

```ini
call 1: imported=1 watermark=1790294400000000                # 只有较新的有效记录，水位推进
call 2 (bad appears): imported=0 watermark=1790294400000000   # 坏记录被跳过，水位不动
call 3 (fixed, older than watermark): imported=0 ids=[good-new]
-> GAP CONFIRMED: corrected record unreachable
```

**缺口的确切形状**：

1. 水位代表「此时间之前已全部处理」，但这是**在坏记录尚未出现时**得出的结论；
2. 坏记录随后出现（或其时间戳被修正）且落在**水位之下**；
3. 下次请求以水位为 `start_time`，该记录**不在请求范围内**；
4. 即使它在范围内被返回，`occ_us < watermark` 的守卫也会 `continue` 跳过；
5. 结果：修正后的记录**永久不可达**。

这与 §3 测到的行为**并不矛盾**：工作树的修复保证了「坏记录在场时不推进水位」，覆盖了「坏记录先出现」的路径；
它**没有**覆盖「水位已定、坏记录后至」——那是**历史范围重新开放**问题，不是单次排空问题。

**因此你的判定成立：边界 1 在当前工作树下仍可复现。§3 的「当前已修复」结论予以撤回。**
